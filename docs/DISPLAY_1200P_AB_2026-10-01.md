# 1200p sustained display investigation

Goal: >=50 Android-drawn frame generations/sec at 1920x1200, normal GNOME motion.
No Git publication. GOOD backup, P7 platform, firmware/kernel/ISO, GPU, boot,
installation, audio, keyboard and persistent user data are preserved.

## Measured, not inferred from a refresh-rate setting

User reports ~30 FPS at 1280x800 and ~half at 1920x1200.
Installed scraper help confirms PollingCycle=30 ms, MaxProcessorUsage=35,
FrameRate=60. Its real argv has no overrides.

One reversible scraper test used the same active GNOME terminal window, 1,800
WM movement requests over 30 seconds per phase at 1920x1200. Requests are not
claimed as rendered/source FPS. Default versus 8 ms / 100% / 120 settings stayed
around 17–18 Android drawn updates/sec. Acquisition+encoding was 45–70 ms/update;
vsock write 1.5–2 ms; Android preparation 3–5 ms. Typically 350–500 rectangles
per update. Original service and 1280x800 were restored automatically.

Separate local RFB profiles (second observer client, discard output, cProfile
active) are NOT end-to-end acceptance and are not strictly matched dirty areas:

The source profiler includes concurrent motion-thread effects; its cumulative

## Follow-up: full-area capture changes the source conclusion

One paired source-only test on the same 1920x1200 desktop used RecordArea rather
than RecordMonitor, native BGRx, and stopped only the competing RFB scraper.
Real terminal-window motion was requested at 60 Hz for 20 seconds.
Full-area 1920x1200 delivered 53–58 samples/sec in most active one-second bins
(49.37 over the entire 21.83-second interval including startup/idle). Non-black
9,216,000-byte frames PASS. GNOME CPU ~45.5% of one core; Xorg ~8.1%, PipeWire
~0.5%, probe Python ~3.5%. CPU counters are process CPU usage, not GPU stall timing.
This refutes treating the earlier 35–40 monitor result as a proven GNOME ceiling.

The 1024x768 area alternated between ~4–23 and ~41–58 samples/sec as damage entered
and left its crop; average 28.63 is NOT a bandwidth bottleneck measurement.
Mutter 46.2 area source explicitly skips redraws outside the requested region:
https://raw.githubusercontent.com/GNOME/mutter/46.2/src/backends/meta-screen-cast-area-stream-src.c
Therefore the small-versus-large comparison is confounded by damage coverage;
do NOT conclude smaller capture is slower or CPU power is insufficient.

Evidence: `mutter-area-1024x768.json`, `mutter-area-1920x1200.json` in the LZ4 build
directory. Scraper and 1280x800 restored, no VM reboot or production replacement.
Next minimal proof: full-area Mutter capture -> bounded latest-frame queue ->
WAVF/LZ4 -> existing 4052 -> existing Android decoder. Preserve original RFB as
fallback and input loop. Must measure Android-drawn updates; source >=50 alone
does not meet the product target. Do not repeat RecordMonitor/crop flag sweeps.

Rollback **before downgrading APK**: inside Ubuntu run
`sudo python3 /tmp/uavf-lz4-ab.py --rollback`, then next display connection uses
the untouched original bridge. If the temporary installer is missing, inspect
the exact drop-in contents and remove only that named diagnostic override, then
`systemctl daemon-reload`. Retain candidate/evidence files; no broad cleanup.

Remaining architecture alternatives: genuine compositor/PipeWire capture
